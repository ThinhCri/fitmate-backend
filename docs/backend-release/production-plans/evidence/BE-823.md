## 1. Hiện trạng và Mục tiêu
- **Mục tiêu**: Xây dựng hạ tầng và bộ kịch bản kiểm thử tải độc lập, đo đạc năng lực xử lý (capacity), độ trễ (latency), hành vi tranh chấp đặt lịch (slot race condition) và hiệu năng phân trang sâu (deep pagination) của Fitmate Backend theo tiêu chuẩn P0, BR-16.
- **Yêu cầu kỹ thuật cốt lõi**:
  1. **Hạ tầng cô lập hoàn toàn (`compose.perf.yml`)**:
     - Tên dự án Docker Compose: `fitmate-perf`.
     - Cổng dịch vụ riêng biệt: Database PostgreSQL `5433:5432`, API container `8088:8080` (tránh hoàn toàn va chạm socket dev).
     - Database chuyên dụng: `fitmate_perf`, volume `fitmate-postgres-perf-data`.
     - Phiên bản k6 cố định: `grafana/k6:0.54.0` kèm volume export kết quả raw json `/results`.
  2. **Tách biệt hai chế độ Rate Limit**:
     - *Chế độ Kiểm thử Bảo vệ (Protection Mode)*: Giữ nguyên mức cấu hình production (60 req/min cho general, 5 req/min cho auth) để kiểm chứng hệ thống phản hồi 429 ProblemDetails đúng chuẩn khi bị spam.
     - *Chế độ Đo Capacity (Capacity Measurement Mode)*: Nâng budget qua biến môi trường container (`PERF_RATE_LIMIT_PER_MINUTE_PER_IP=10000`, `PERF_RATE_LIMIT_AUTH_PER_MINUTE_PER_IP=2000`, `PERF_RATE_LIMIT_AUTH_REFRESH_PER_MINUTE_PER_IP=4000`) để đo thông lượng thực tế của engine mà không bị nghẽn ở lớp limiter. Báo cáo ghi nhận rõ ràng mức budget này để tránh kết luận sai lệch về cấu hình production.
  3. **Pool tài khoản giả lập & Xử lý Admin MFA**:
     - Member pool: 100 tài khoản (`perf_member_001@fitmate.vn` .. `perf_member_100@fitmate.vn`).
     - PT pool: 20 tài khoản (`perf_pt_001@fitmate.vn` .. `perf_pt_020@fitmate.vn`).
     - Phân bổ 1-1 theo VU ID (`__VU`), loại bỏ hiện tượng các VU dùng chung 1 tài khoản làm sai lệch cache và lock.
     - Token cache: Giữ cache token trong memory của k6 VU, chỉ làm mới khi token còn dưới 60 giây hạn sử dụng (`resetCaches()`).
     - **Admin MFA**: Hợp đồng `AuthController.cs` hiện chưa triển khai bước challenge/verify MFA khi đăng nhập (chỉ có endpoint cài đặt MFA sau khi đã đăng nhập). Để đảm bảo trung thực, kịch bản **ghi nhận rõ kịch bản Admin bị BLOCKED** do thiếu hợp đồng đăng nhập MFA, tuyệt đối không bypass hoặc giả mạo token.
  4. **Dataset đại diện & Phân trang sâu có dữ liệu thực**:
     - Dataset chuẩn đại diện: 600 members, 60 PTs (đầy đủ Approved NASM Certificate để hiển thị trên marketplace), 1.000 bookings, 2.000 meal logs, 1.000 workouts.
     - Bookings phân bổ theo từng user: 10 users chỉ định (từ `perf_member_001` đến `perf_member_010`) mỗi người sở hữu ít nhất 60 bookings. Điều này đảm bảo khi kiểm thử trang sâu (`/me/bookings?page=5&pageSize=10`), hệ thống truy vấn và trả về đủ 10 bản ghi thật đã đánh chỉ mục, không phải trang rỗng.
     - Chốt chặn CLI Seeder (`SeedPerfDataCommand`): Từ chối chạy trên Production (`ASPNETCORE_ENVIRONMENT=Production`), bắt buộc cờ `--allow-perf-seed` hoặc `PERF_SEED_ENABLED=true`, và kiểm tra nghiêm ngặt tên database đích phải chính xác là `fitmate_perf`.
  5. **Kiểm thử tranh chấp chỗ (Slot Contention)**:
     - Kịch bản `contention.js`: 20 VU riêng biệt cùng lúc gửi yêu cầu giữ chỗ (`POST /api/v1/bookings/holds`) cho duy nhất một slot khả dụng của PT.
     - Tích hợp khóa đồng bộ Semaphore theo slot trong `BookingService.CreateHoldAsync`.
     - Assertion tuyệt đối (zero-tolerance):
       - `holds_succeeded == 1` (duy nhất 1 request nhận HTTP 201 Created).
       - `conflicts_received == 19` (chính xác 19 request nhận HTTP 409 Conflict với error code `BOOKING_SLOT_TAKEN`).
       - `unexpected_failures == 0` (0 lỗi 500 hoặc unhandled exception).
  6. **Phân tích N+1 truy vấn SQL**:
     - Đánh giá N+1 dựa trên sự tăng trưởng số lượng truy vấn theo kích thước trang (`pageSize=10` vs `pageSize=50`), không giả định phân trang chỉ thực thi duy nhất 1 câu lệnh SQL (vì EF Core phân trang tiêu chuẩn thực thi 2 query: `COUNT(*)` và `SELECT ... LIMIT ... OFFSET`).
